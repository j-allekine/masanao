## Problem Statement

Staff need to prepare and record supplies for a Meal Schedule containing multiple Recipes and separately issued stock Items. Today the application has receiving stock-in but no production issuance workflow. The prototype demonstrates the desired interaction but uses in-memory illustrative data. Copying it directly would omit persistent drafts, reliable scaling, Item conversions, quantity review, authorization, and accountable stock-out posting.

## Solution

Create the Meal Schedule's single Issuance Record with saved draft preparation and one explicit Post issuance action. Prefill Meal pax from Activity Planned pax, add Recipes or Stock items through one searchable Add dropdown, calculate copied Recipe ingredients, and review ingredients in a side panel. Combine demand by Item in Base Units, allow secondary final-quantity adjustments, warn about fractional whole-only totals, and deduct the confirmed totals atomically after checking available stock. Posted issuance is final and read-only.

## User Stories

1. As kitchen staff, I want to open issuance from its Meal Schedule, so that I prepare supplies for the correct meal rather than a disconnected record.
2. As kitchen staff, I want the Activity and Meal Schedule context visible, so that similarly named meals are not confused.
3. As kitchen staff, I want Meal pax initially taken from Activity Planned pax, so that I do not reenter the normal count.
4. As kitchen staff, I want to supply Meal pax when planning has no positive count, so that calculations never assume one diner.
5. As kitchen staff, I want to change draft Meal pax, so that the preparation can differ from the Activity plan.
6. As kitchen staff, I want saved draft pax unchanged by later Activity edits, so that my prepared quantities are not silently rewritten.
7. As kitchen staff, I want one Add dropdown offering Recipe and Stock item, so that both supply paths are clear without cluttering the toolbar.
8. As kitchen staff, I want to search reusable Recipes and see their baseline pax, so that I can select the correct food.
9. As kitchen staff, I want the Recipe picker prefilled with Meal pax, so that normal additions need no second count.
10. As kitchen staff, I want to change pax inside the Recipe picker for newly added Recipes only, so that an exception does not change existing foods.
11. As kitchen staff, I want to add several different Recipes through the searchable picker, so that a meal can contain multiple foods efficiently.
12. As kitchen staff, I want incomplete legacy Recipes clearly unavailable for scaling, so that ingredient quantities are not guessed.
13. As kitchen staff, I want a compact Recipe table with secondary pax-adjustment actions, so that the normal case stays simple.
14. As kitchen staff, I want to click a Recipe or choose View ingredients to open a side panel, so that the main list does not expose every ingredient.
15. As kitchen staff, I want Baseline and To issue quantities in the side panel, so that I can understand the calculation.
16. As kitchen staff, I want selected Recipe data preserved as a snapshot, so that later master edits do not rewrite the draft or posted issuance.
17. As kitchen staff, I want to add a stock Item such as bottled water without a Recipe, so that direct supplies do not need artificial foods.
18. As kitchen staff, I want to enter stock quantity and an Item-supported Unit, so that packages are converted correctly without assuming one per pax.
19. As kitchen staff, I want Recipes and Stock items displayed in separate sections but posted together, so that the page is understandable and deductions are complete.
20. As kitchen staff, I want combined Item requirements checked across all foods and stock lines, so that the same inventory is not independently promised several times.
21. As kitchen staff, I want a warning icon and visible explanation for fractional whole-only demand, so that I know what requires review.
22. As kitchen staff, I want fractions that combine into a whole total accepted, so that 12.5 plus 12.5 eggs does not force 26 eggs.
23. As kitchen staff, I want a secondary Adjust issued quantity action for a combined Item total, so that the deducted amount matches the supplies actually taken.
24. As kitchen staff, I want the original calculation retained alongside a confirmed adjustment, so that the difference is understandable later.
25. As kitchen staff, I want affected demand changes blocked until I explicitly reset an adjustment, so that an old confirmation cannot survive a different requirement.
26. As kitchen staff, I want to save and reopen an incomplete draft without stock movement, so that preparation can span sessions.
27. As kitchen staff, I want visible shortages before posting and a fresh check when posting, so that I cannot overdraw inventory.
28. As kitchen staff, I want Post issuance to record all stock-out or none, so that failure cannot leave half a meal issued.
29. As kitchen staff, I want repeated clicks or network retries not to deduct twice, so that a single posting stays single.
30. As kitchen staff, I want conflicting draft saves reported rather than silently overwriting another user's work, so that shared preparation is safe.
31. As an administrator, I want the same preparation and posting access as kitchen staff, so that I can operate the kitchen workflow.
32. As any unauthenticated user, I must not be able to read or mutate issuance, so that operational records remain protected.
33. As kitchen staff, I want a final posting confirmation and read-only posted detail, so that I understand there is no edit, deletion, or correction in this release.
34. As a keyboard, screen-reader, or mobile user, I want accessible pickers, warnings, dialogs, errors, and responsive tables, so that the complete workflow is usable.

## Implementation Decisions

- Introduce an Issuance feature owning its UI, validation, public reads/actions, draft commands, posting transaction, and persisted issuance data. Follow existing feature gateways and keep server/data-access rules out of presentation components. Extend the combined Prisma model only for real workflow data; do not create unnecessary architectural layers.
- Depend on the completed Recipe Baseline Pax and Item issuance-quantity policy capabilities. Use their supported public reads. No duplicate Recipe setup or Item policy ownership in issuance.
- A Meal Schedule has zero or one Issuance Record, created when the first supply line is successfully saved. Draft and Posted are the lifecycle states. Enforce uniqueness in persistence, including concurrent creation.
- Reopening returns that same record. Removing the last draft line may leave an empty saved draft; it cannot be posted and does not create another record. Do not add a draft-record deletion or replacement workflow in this slice. Leaving with unsaved changes requires a discard confirmation; Save draft makes the current changes persistent.
- Open the workflow from the existing Meal Schedule record hierarchy. Keep Activity Design, Activity, and Meal Schedule context identifiable. Do not introduce an independent schedule layer or finished-food inventory.
- As associated Planning work, rename Activity Planned participants to Planned pax without losing its stored value. Retire Meal Schedule Planned servings from active create/edit/display and defaulting. Preserve legacy stored values during an additive transition; inventory existing data before any destructive removal. Column deletion is not necessary for this slice and must not silently discard data.
- Stop accepting Planned servings as an active planning input, but preserve its legacy stored value when a Meal Schedule's label/time is edited. Omission from the new form must not write null over an existing value. Retain it only for transition/data preservation, not an active fallback or second user-facing count.
- Initial Meal pax comes from positive Activity Planned pax only. If absent or zero, require explicit positive whole-number Meal pax before Recipe calculations or posting. Incomplete drafts can be saved with missing pax. Existing draft defaults never automatically track later Activity changes.
- Meal pax and explicit Recipe target pax use the same 1 to 2,147,483,647 bounds as Recipe baseline pax. Require valid Meal pax and picker target pax before adding Recipes. Existing selected snapshots can remain in an incomplete saved draft if required pax is subsequently cleared, subject to adjustment locks. Blank required pax marks meal calculations pending, not zero demand; do not present known contributions as a complete meal requirement or complete availability check. Direct-stock-only drafts still require Meal pax to post, consistent with the approved meal workflow.
- New Recipe additions inherit Meal pax unless the picker value differs. A changed picker count applies only to Recipes added in that session; reopening prefills the current Meal pax. Preserve secondary per-Recipe adjustments and which targets follow the draft meal default. Changing Meal pax recalculates inherited targets, not explicit per-Recipe targets.
- Copy Recipe identity/name, baseline pax, ingredient Item identities/names, entered quantities, selected Unit identities/names, and conversion factors into Recipe Snapshots when selected. Preserve the snapshot during saving and future calculation; do not fetch a new master ingredient list on every recalculation. Later master or conversion changes do not rewrite existing snapshots. Reject new selection of inactive or missing-baseline Recipes.
- Obtain canonical source data on the server when creating a persisted snapshot; do not trust browser-submitted baseline, Item identity, conversion factor, or ingredient quantities. After creation, save existing snapshots by identity/revision and allowed target changes without refreshing or accepting arbitrary ingredient replacements. Store independent ingredient snapshot rows rather than references that would be deleted when the master Recipe editor replaces its ingredient rows.
- Before the first save, associate selection/preview with a server-verifiable source revision. If the Recipe or conversion changes between preview and snapshot persistence, require reselection/review instead of silently substituting different quantities. After the snapshot is persisted, its copied reference data is authoritative for that draft. No inventory effect occurs in either case.
- Direct-use stock selections also snapshot selected/base Unit identifiers, display labels, conversion factor, and exact entered quantity. Editing their selection/quantity deliberately validates the selected active Item/Unit and applies the current conversion; reopening or saving unchanged lines does not silently rebase them.
- Restrict deletion of Recipes and Items referenced by saved issuance, and protect Item Base Unit changes while saved issuance references exist. Preserve current conversion edit/removal constraints; historical snapshots must not cascade away. A later master Recipe edit or deactivation does not refresh or invalidate an existing Recipe Snapshot merely because its source changed. Posting does recheck that the underlying stock Items and selected/base Units remain active/available and that Base Unit identity still agrees; surface any failure without modifying the draft.
- Keep prototype A's hierarchy: fixed top context/controls, one Add dropdown, searchable selection, compact Recipe list, separate Stock item section, secondary actions, and ingredient Sheet. The list scrolls while top controls remain available. No summary cards or default-expanded ingredients. Use current design tokens, shared workspace presentation, shadcn primitives, accessibility, and responsive behavior; the prototype's data and code are not production specifications.
- A Recipe can be selected once per issuance, as in the prototype; use its pax adjustment instead of silently adding duplicates. Direct-use stock lines select active Items and their Base Unit or configured alternate Item Unit, with explicitly entered positive exact-decimal quantities. No global conversion inference, automatic one-per-pax quantity, new Item type, or inline Recipe creation.
- Calculate Recipe demand as snapshotted entered quantity multiplied by target pax and divided by baseline pax, then convert to Base Units using the snapshotted Item factor. Combine Recipe and direct-use requirements by Item across the meal before final rounding, whole-only validation, availability checks, or ledger posting.
- Use exact decimal/rational arithmetic, not binary floating-point approximations. Preserve source and accepted manual decimals. For automatic decimal-allowed combined Base Unit totals, round once to six places using nearest, with an exact halfway case rounded away from zero; trim trailing zeros for display. This tie rule is a specification detail completing the approved nearest-rounding policy, not a new automatic whole-unit rule.
- A combined total involving scaled Recipe demand is an automatic total subject to this one-time rounding. A direct-stock-only Item total is an exact sum of entered-and-converted quantities and remains exact, as does an explicit final Base Unit adjustment. Do not apply a six-place input cap or round away precision that staff explicitly entered. Save the exact calculated provenance and the final posting quantity separately.
- Evaluate unadjusted whole-only demand against the exact combined Base Unit total before decimal rounding. A fractional calculated total requires review, but a valid explicitly confirmed whole-number final quantity resolves the posting block: for example, calculated 18.5 eggs may be confirmed as 19 eggs. Posting validates the exact confirmed final quantity when adjusted, not the original fraction. Never ceil individual Recipes. Fractional alternate packaging is acceptable when conversion results in a valid combined Base Unit total. Positive demand rounding to zero remains visible and requires an explicit positive final adjustment before posting.
- The ingredient Sheet has Baseline and To issue columns. Its Recipe quantities remain calculated contributions; if a combined total is adjusted, visibly identify that fact and provide access to the combined Item review without distributing the difference arbitrarily among Recipes.
- Both Sheet column headings include their pax context and each quantity shows its Unit. Finite baseline quantities retain their exact display. For repeating per-Recipe calculations, show a compact six-place approximation clearly marked as approximate and explain that final deduction uses the combined Item review quantity. The review and final posting confirmation display the exact final ledger quantity, not a separately rounded visual estimate.
- A secondary review dialog provides the combined calculated Base Unit requirement and editable confirmed issued total. Adjustments belong to issuance Item totals, not master data or individual Recipe ingredients. Retain calculated total, final total, adjustment state, and policy used at posting. No mandatory variance-reason field was approved for this pre-post adjustment.
- Confirmed final quantities must be positive and must be whole when the current Item policy requires it. An adjustment cannot silently remove an Item by entering zero. Explicitly choosing the same value as the computed final quantity clears redundant adjustment state. The server validates all quantity edits and lock/reset rules, not just the browser.
- A warning icon must have an accessible label and visible text, not hover-only or color-only communication. Fractional whole-only contributions may be informational when the combined total is whole; unresolved fractional final totals block posting and link to review.
- An adjusted Item total locks every operation that would alter its demand: affected meal/Recipe pax changes, affected Recipe additions/removals, and affected direct-stock edits. Explain which adjustment must be reset. Explicit reset removes that confirmation and unlocks affected operations. Unrelated additions remain possible. Do not silently preserve or erase stale adjustments.
- Explicit Save draft persists snapshots, pax, supply lines, confirmed combined quantities, and edit state without inventory changes. Use optimistic revision checks to reject stale draft saves/posts with a recoverable conflict message rather than last-write-wins data loss. Posting uses the persisted current draft revision; unsaved edits must be saved/validated before final confirmation.
- Authenticated kitchen staff and administrators can read, prepare, save, and post issuance. Existing Recipe/Item setup privileges remain unchanged. Enforce authorization on the server for every read and mutation, not only visible buttons.
- Availability is the authoritative Item Base Unit balance from posted ledger movements, including stock-in and prior stock-out. Do not treat received-only totals as on hand. Display shortages with Item, required final quantity, available quantity, and Unit. Draft checks are advisory; posting rechecks authoritatively.
- Extend the existing ledger model, whose current movement source is a required Delivery Receipt Line, to support issuance Item-total sources as well. Keep positive quantity magnitudes with explicit stock-in/stock-out direction; balance equals stock-in minus stock-out. Enforce exactly one valid source appropriate to the direction and unique source-to-movement identity. Do not invent Delivery Receipt lines for stock-out, use fake receipts, or create a disconnected second ledger. Preserve existing stock-in rows and the current one-movement-per-receipt-line guarantee during migration.
- One explicit Post issuance action validates current draft, required pax, line eligibility, final positive quantities, whole-only totals, and aggregate availability; atomically records posting-time evidence and immutable stock-out movements and marks the record Posted. Use transaction/locking behavior suitable for the existing database, a conditional Draft-to-Posted transition, and unique posting/movement identity to prevent duplicate or concurrent overspending. Any failure leaves no partial posting or deduction.
- Treat an already successful posting retried for the same record as the existing posted result, not another write. A stale draft/revision conflicts rather than posting unseen changes. Re-read live Item policy inside posting; a changed policy can introduce a blocking warning and must not silently round the draft. Return actionable errors for shortages, inactive/missing references, policy conflicts, stale drafts, and busy/concurrent writes; no branch may leave partial inventory movements.
- Record final combined Base Unit stock-out by Item under the Issuance Record while retaining food/stock contribution evidence in snapshots. Do not allocate final adjustments arbitrarily to individual foods. Store posting actor/time, source Meal Schedule context, Item/Unit display evidence, source calculations, final quantities, and quantity policy for historical review.
- Posted reads display persisted posting evidence and quantities. Later Recipe, planning, Item-name, Unit-name, or quantity-policy edits must not recalculate or relabel that evidence as if it were the current master data. Live policy revalidation applies to draft posting, not retrospective validation of posted records.
- Posted records and movements cannot be edited or deleted through any supported action. Protect parent deletion where posted/draft issuance references exist, and surface a meaningful restriction. Provide an explicit final confirmation stating that no correction, reversal, return, or replacement posting is available in this release.

## Testing Decisions

- Prefer a high-level public Issuance command/query integration seam with an isolated real database, following Recipe persistence and receiving stock-in tests. Exercise draft preparation, reload, adjustment/reset, posting, permissions, and public historical reads; inspect persisted ledger effects as outcomes, not internal function calls.
- Use existing authenticated Server Action testing patterns for authentication/authorization failures and rendered action validation. Avoid test-only HTTP APIs or unnecessary layers.
- Test zero-or-one record enforcement, concurrent first-save attempts, stale revisions, retry/double-click idempotency, concurrent competing postings, and failure rollback. Use real independent operations; mocks alone are insufficient evidence for stock safety.
- Run concurrent-stock tests using distinct database connections to the same isolated database, not independently isolated databases or one sequential connection. Inject a failure after an early stock-out insert to prove rollback, and prove legacy receipt movements survive the ledger-source migration unchanged.
- Cover Recipe snapshots unchanged by master edits, Item conversion snapshots, inherited versus explicit targets, picker-specific pax, missing-baseline selection, inactive reference behavior, and missing/zero Activity pax without legacy Meal Schedule fallback.
- Prove 12.5 plus 12.5 eggs becomes 25, fractional trays can become whole eggs, Recipe and direct-stock demand combine, decimal totals round only after aggregation, exact halfway cases behave deterministically, and tiny positive quantities are not silently omitted.
- Cover confirmed final quantities used identically by display, availability, and ledger deduction; adjusted demand locks/reset; unrelated additions; unresolved fractional blocking; and policy changes checked at posting without rewriting history.
- Explicitly prove that 18.5 calculated eggs blocks unadjusted posting, confirmation of 19 permits posting when stock suffices, and exactly 19 is deducted. Prove clearing required pax leaves a saveable pending draft but prevents Recipe additions, misleading complete totals, and posting. Verify posted reads remain unchanged after later master-data and policy edits.
- Cover incomplete draft saves without movements, shortage failures without any movement, successful full posting, immutable posted actions, parent deletion protections, staff/admin access, and unauthenticated rejection.
- Extend current Planning coverage to verify the Planned pax label, removal of active Planned servings controls, preservation of legacy data, and unchanged hierarchy.
- Verify retired planning counts survive label/time edits, removed last lines leave an unpostable empty draft, failed posting retains the draft, master ingredient replacement cannot delete snapshots, direct-stock factors survive reopen, browser-tampered snapshots are rejected, and server lock enforcement cannot be bypassed by submitted forms.
- Use focused browser journeys through Meal Schedule, Recipe picker, Stock item picker, ingredient Sheet, warnings, combined review, Save draft/reopen, and final posting/read-only detail. Include keyboard/focus, screen-reader labels, visible errors, responsive desktop/mobile, fixed-header scrolling, and no clipping/overflow. Do not accept green CI alone as proof of the requested UI.
- Run migrations against existing-data fixtures, relevant integration/browser tests, lint, type checks, Prisma validation/generation, and production build. Require browser evidence for affected Planning, Recipe selection, Item reference, and issuance states.

## Out of Scope

- Corrections, reversals, returns, posted edits/deletion, replacement issuance posting, partial posting, or negative-stock overrides.
- Finished-food inventory, production manufacturing orders, nutrition, yield-loss, waste, procurement lines, approvals, locations, lot/batch/expiry or FEFO allocation, and a standalone Inventory dashboard.
- Inline creation of reusable Recipes, arbitrary ingredient substitutions/additions in a Recipe Snapshot, permanent master edits from issuance, and invented adjustment allocations to foods.
- Automatic whole-unit rounding, global Unit restrictions, silently tracking later planning changes, and destructive removal of legacy planning data without explicit migration handling.
- New setup permissions, external integrations, or importing illustrative prototype data into production.

## Further Notes

- This is specification 3 of 3, blocked by Recipe baseline setup and Item issuance-quantity policy. The Planning label/field transition is a bounded prerequisite inside this workflow specification, not a fourth standalone module spec.
- ADR 0005 establishes Meal Schedule as the issuance context; ADR 0004 governs Item-specific conversions; ADR 0006 provides the existing accountable posting precedent; ADR 0007 records this workflow's accepted boundaries.
- Prototype A is currently available locally at http://localhost:3117/prototype/recipe-scaling?variant=A. Capture a portable visual reference before relying on it from another checkout or an unattended issue; localhost is not a remotely available artifact.
- Posting is intentionally irreversible in this scope. Quantity confirmation and clear finality warnings mitigate mistakes but do not provide a correction mechanism.
- Keep specification dependencies visible in the tracker. Recipe and Items may run independently; do not start stock-out delivery before both contracts are available.
